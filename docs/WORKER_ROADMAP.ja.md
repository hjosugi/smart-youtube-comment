# ワーカーのロードマップ

## 現在のリリース

リレーはステートレスなHTTPポーリングを維持しています：

- エッジキャッシュは同じキーの温かいポーリングを圧縮します。
- 隔離内のフライト中の圧縮は冷たいバーストを保護します。
- オプションの `ALLOWED_ORIGINS`（カンマ区切りのオリジン）は、信頼されたアプリ以外のブラウザ呼び出しをブロックします。
- `RATE_LIMIT_PER_MINUTE` は各クライアントIPごとに隔離ごとに制限します（デフォルトは `120`、 `0` は無効）。
- 構造化されたメトリクスは、キャッシュ、フライト中、上流のレイテンシ、および再試行回数を報告します。

リプレイ継続ポーリングは明示的です：

```text
/api/livechat?cont=<token>&offset=<ms>&replay=1
```

リプレイの最終状態は埋め込まれたプレーヤーが所有します。リレーはリプレイエンドポイントが任意のオフセットでクエリ可能であるため、リプレイ `ended: false` を維持します。

## 耐久オブジェクトのシングルフライト候補

HTTPポーリングメトリクスがエッジキャッシュとフライト中の圧縮が不十分であることを示した後にのみ、WebSocket + 耐久オブジェクトに移行します。必要な証拠：

- 同じビデオの多くの視聴者に対する高いMISS率、
- キャッシュHIT比率の調整にもかかわらず上流の429/5xxバースト、
- 繰り返しの再解決または継続のチャンのクライアント可視レイテンシ。

候補アーキテクチャ：

1. YouTubeビデオIDごとに1つの耐久オブジェクトインスタンス。
2. クライアントはWebSocketで接続し、リプレイのための現在の再生オフセットを送信します。
3. DOはライブ継続ごとに1つの上流ポールループを所有します。
4. DOは接続されたクライアントに正規化された `PollEnvelope` バッチをブロードキャストします。
5. HTTP `/api/livechat` はWebSocketの採用が測定されるまでフォールバックとして残ります。

受け入れゲート：

- 追加のスコアリング/レンダリング作業がワーカーに移動しないこと、
- ビデオごとのDOメモリが切断のチャンの下で制限されること、
- リプレイオフセットがグループ化またはサンプリングされているため、1つのスクラバーが上流リクエストの増幅を強制できないこと、
- メトリクスがHTTPとDOパスの上流呼び出し、レイテンシ、およびエラーを比較します。
