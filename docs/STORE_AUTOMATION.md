# Chrome Web Store Automation

This repo can automate repeat Chrome Web Store updates after the one-time store
setup is complete. The extension source stays JavaScript-only; the store upload
path only packages the existing `extension/` directory and submits the zip.

For the no-thinking, step-by-step Japanese runbook, use
`docs/STORE_RELEASE_RUNBOOK_JA.md`.

## What Can Be Automated

- version consistency checks
- security checks and local tests
- zip, checksum, release metadata, notes, and tester guide generation
- Chrome Web Store package upload
- upload-processing polling
- publish/review submission
- GitHub Actions artifact retention

## One-Time Manual Setup

These steps still require a browser because Chrome Web Store ownership, OAuth,
store listing, and privacy declarations are account-bound:

1. Create or select the Chrome Web Store developer account.
2. Create the extension item in the Chrome Web Store Developer Dashboard.
3. Fill in listing copy, screenshots, category, support, privacy, and data-use
   declarations.
4. Enable the Chrome Web Store API in Google Cloud.
5. Choose one CI authentication path.

Preferred: service account plus GitHub OIDC / Workload Identity Federation. Add
the service account to the Chrome Web Store publisher and store these GitHub
repository secrets:

```text
CHROME_WEBSTORE_PUBLISHER_ID
CHROME_WEBSTORE_EXTENSION_ID
GCP_WORKLOAD_IDENTITY_PROVIDER
GCP_SERVICE_ACCOUNT
```

Fallback: OAuth refresh token. Create OAuth credentials, authorize the publisher
account with the `https://www.googleapis.com/auth/chromewebstore` scope, generate
one refresh token, and store these GitHub repository secrets:

```text
CHROME_WEBSTORE_PUBLISHER_ID
CHROME_WEBSTORE_EXTENSION_ID
CHROME_WEBSTORE_CLIENT_ID
CHROME_WEBSTORE_CLIENT_SECRET
CHROME_WEBSTORE_REFRESH_TOKEN
```

`CHROME_WEBSTORE_ACCESS_TOKEN` can be used locally instead of the client/secret/
refresh-token trio, but GitHub Actions should prefer the refresh-token flow or a
short-lived token generated by Workload Identity Federation.

## Local Release Commands

Run all checks, build the release zip, upload it, and submit it:

```sh
npm run release:store
```

Upload without publishing:

```sh
npm run release:zip
npm run release:store:upload
```

Publish after a successful upload:

```sh
npm run release:store:publish
```

Check store status:

```sh
npm run release:store:status
```

Dry-run the API call shape without network access:

```sh
node scripts/chrome-webstore.mjs submit --dry-run
```

## GitHub Actions Release

The workflow lives at `.github/workflows/chrome-webstore-release.yml`.

Normal path:

```sh
npm run version:set -- 0.1.1
git commit -am "Release 0.1.1"
git tag v0.1.1
git push origin main --tags
```

Pushing a `vX.Y.Z` tag runs checks, packages the extension, uploads release
artifacts, uploads the zip to Chrome Web Store, and submits it for
review/publishing. The workflow rejects a tag if it does not match the package
roots updated by `npm run version:set` and `extension/manifest.json`.

Manual emergency path:

1. Open the `Chrome Web Store Release` workflow.
2. Enter an optional version.
3. Use `status_only: true` to test access without consuming a version, or
   `status_only: false` for an upload/publish run.
4. Choose whether to publish immediately or upload only.
5. Run the workflow.

Manual version overrides are intended for emergencies because they do not commit
the version bump back to the repository.

## Optional Controls

- `CHROME_WEBSTORE_SKIP_REVIEW=1`: request review skipping when eligible.
- `CHROME_WEBSTORE_DEPLOY_PERCENTAGE=25`: request staged rollout percentage.
- `CHROME_WEBSTORE_BLOCK_ON_WARNINGS=0`: allow publish despite API warnings.
- `CHROME_WEBSTORE_UPLOAD_POLL_ATTEMPTS=24`: upload-processing poll count.
- `CHROME_WEBSTORE_UPLOAD_POLL_DELAY_MS=5000`: delay between status polls.

By default, publishing blocks on Chrome Web Store API warnings. This keeps the
automation from turning a policy or validation warning into an accidental public
release.

## Rollback

Chrome Web Store does not provide an instant source-level rollback from this
repo. If a bad version reaches review or publication:

1. Stop or pause the release in the Developer Dashboard when possible.
2. Bump the patch version.
3. Re-run the automated release with the fix.
4. Keep the bad `.release/*.release.json` metadata for audit/debugging if the
   artifact was already shared.
